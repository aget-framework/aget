### Fleet migration kit

The kit is for the supervisor of a fleet. It is not installed into member Agets and it is not part of any template. A supervisor copies `scripts/migration_kit/` from a clone of the core repository, checked out at this release, into the supervisor's own repository and commits it there. The kit carries no default release: `release_target.py` reads the source and target versions, the fleet register pin and the member count from `.aget/migration_target.json` or from `AGET_MIGRATION_*` environment variables. Nine tools (the prepare, plan, apply, packet-rehearsal, push, ledger and readiness tools) stop without a target and say how to set one; the others, among them `launch_batch.py`, `record_authority.py`, `rehearse_v37.py` and `suite_at_commit.py`, make no such check.

What the tools do, in the order the procedure uses them:

- Prepare: `prepare_batch.py` and `prepare_launch.py` build the batch's protected-path list and launch packet from each member's working tree and the release's bytes at their tags, and `prepare_write_list.py` builds the write list from those two. Each writes its result to the file named with `--out`; `prepare_launch.py` also stages release files, the placer and one settings file per receiver in a new packet root beside the `--out` packet under `<packet folder>/<release>/packets/` by default (`AGET_MIGRATION_PACKET_BASE` overrides; outside every repository), seals that stage before it writes the packet, and, with `--apply-list`, writes an apply list to the file named there, and `prepare_write_list.py` also writes a scope-check result beside its output. `plan_protected.py` is the trial run of the protected write and contains no write. `check_batch_scope.py` and `check_receiver_write_scope.py` check receiver bounds.
- Rehearse on copies: `rehearse_batch2.py` rehearses the packet without a model; `rehearse_v37.py` runs a headless session rehearsal on a copy.
- Record and check authority: `record_authority.py` records the typed line for an act, `check_principal_line.py` reads the transcript of the session it is given and reports whether the newest prompt containing the given text counts as typed, and `batch_authority.py` is the check the push tool calls, and the launch tool calls unless `--copy-root` is given. `check_list_approvable.py` checks that both rehearsal results name the list being approved or, with `--relisted-from`, the rehearsed list given there.
- Act: `apply_protected.py` writes the protected paths from the reviewed list; `launch_batch.py` records baselines and launches receiver sessions; `after_run_check.py` checks each run; `suite_at_commit.py` runs a member's suite in a clean clone at the exact commit to be pushed; `push_batch.py` pushes.
- Read state: `fleet_ledger.py` reports each member's state; `watch_receiver.py` is a read-only watcher that exits on a receiver's turn end, HEAD move or a move of one remote ref (`refs/heads/main` unless `--ref` is given), and also on a failed probe or at its timeout (3600 seconds unless `--timeout` is given); `open_receiver.py` opens a receiver's window when `OPEN <key>` is typed at a terminal, or, with `--preauth` and `--batch`, when a pre-authorization file names that receiver and batch; the file's origin is not checked and no session record is read.

The kit's other Python files:

- `census_fleet_ci.py` lists the fleet register's members that have a name, a location and a workflow at their repository root, with what a text scan of those workflow files finds they need on the runner (a floor, not a complete list). Only with `--online` does it query the state of that repository's newest run, marked stale when that run was not for the checkout's current commit; a repository whose runs cannot then be queried reads as unreachable, never as passing.
- `rehearse_repair.py` rehearses a repair packet on throwaway copies, without a model.
- `run_suite_parallel.py` runs a member's test suite as one process per test file, in parallel, with one summary in pytest's form (each file's own short-summary lines, read by the same reader, under one `short test summary info` header; a file whose failing ids cannot be read, or whose pytest did not finish, gets an `IDS-UNKNOWN` line, never an id); every deselected test is named in the output. Under the kit, each file's pytest also writes the kit's report, and the runner records the one invocation each file's output names; the kit reads the failing ids from that report, never from these lines.
- `verify_extension_survival.py` recomputes from bytes, against a baseline captured before the migration, whether a member's own lines survived it.
- `watch_settings_rules.py` watches a receiver's Claude Code settings files for permission-rule changes during a session; it logs a per-file rule count at start and, for each change it observes at a poll, short digests of the rules added and removed, never rule text.
- `write_scope_rules.py` is the module that reads a receiver's declared write scope.
- `wave_readiness.py` is loaded by other kit tools for functions and constants. Its own readiness run is not part of the batch procedure; see "Gaps in the kit as shipped".

The authority check is per act, and it has limits. A push reads only a line recorded for the push itself (`record_authority.py --act push`), and that line must have one fixed form; it is recorded for one packet (`--packet`, whose digest is kept with the line), and a push from any other packet, even one with the same batch number, is refused; the batch's own line, and a line recorded for the launch, are never push authority, whatever they say. A launch line need not name the launch, but is refused when it matches the launch-exclusion pattern ("do not launch"). For either act the typed prompt that holds the line must name the batch in the first batch list it gives. The push and launch checks, and the baseline-equal ruling check, also accept as typed a line queued while the session was busy: the session's records mark its origin as human, and the tool does not read whether it was typed or an accepted suggestion. Where these notes say one of those three checks needs or finds a typed line, that includes this case. The push line must have the fixed form (the prefix, then `push the commits of batch N`, optionally more batches (`batches 10t and 10`) and ` with commit SHA` (or `commits SHA, SHA and SHA`, each 7 to 40 hexadecimal characters), and nothing else; with the default prefix, `GO supervisor - push the commits of batch 1`) and must equal the whole typed prompt it is found in (runs of whitespace collapsed; a pasted block among other words is left out of the comparison). That is a test of form, not a reading of meaning: a line worded any other way is refused, an affirmative one too, and the principal types the form. A launch with `--copy-root` checks no typed line. See "Authority checks: what the tools do and do not enforce". A line passed as a session's launch argument is refused as authority. A ruling that a failing suite is equal to the member's baseline must carry a line that is found typed and has its own fixed form (the prefix, then `the failures at SHA are baseline-equal`, SHA being 7 to 40 characters the commit's id starts with); that line gets the same whole-prompt test as a push line. `record_authority.py` writes the ruling file; the push tool does not check what wrote the file, so writing it only with `record_authority.py` is an operator rule, not enforced by the tool.

`batch_rules.json` holds narrow permission rules for one supervisor session, passed with `claude --settings`. They last for that session only. Each rule covers its command with any arguments. The three tools the rules name each hold a call to the authority check, but not on every path: `launch_batch.py --launch --copy-root` makes none. `BATCH_SESSION.md` explains how to start the session and why.

The kit declares one dependency, PyYAML 6.0 or newer, in `scripts/migration_kit/requirements.txt`.

`tests/migration_kit/` holds 34 files, including 31 `test_*.py` files. The historical Round 2 kit suite was measured before the Round 2b protected-mode changes with `python3 -m pytest tests/migration_kit -q -p no:cacheprovider`, on Python 3.14.8 and Python 3.12.13; the result is 1523 passed on each interpreter (details below). The 1476-test run on an earlier internal candidate predates later code and test changes. The earlier full core suite measurement gave 1602 passed, 11 skipped; it was not re-measured for this text correction. On an earlier internal candidate, before these release files and those eight changes were added, the kit's tests held 274 test functions and the same commands gave 393 passed and 1471 passed, 11 skipped.

The kit is built, tested and rehearsed with Claude Code only. See "The migration kit: what was shown and what was not".

### Kit batch procedure and close-out gate

`sops/SOP_fleet_migration.md` moves from v1.9.0 to v1.10.8. The existing phases (pilot, main, secondary) still decide which Agets go in which batch. The new "Kit Batch Procedure" section decides how a batch runs. It has a setup table for each release, a table of per-release inputs (Part A) and fifteen fixed steps with a pass condition and an actor for each (Part B: B0 to B13, with B8a). The procedure says to stop at the first failure and that INCONCLUSIVE is never PASS. These are rules for the supervisor to apply from the printed verdicts: a live launch at B8 exits 0 whatever its after-run checks said, and the push tool prints NOT PUSHED for a receiver its gate refuses without changing its exit code, which is 0 when the gate refuses every receiver and 1 when a push that ran was not confirmed.

The procedure marks two steps as having no tool of their own yet and writes them as manual criteria: membership (B0, hand checks on the unmet rows that `fleet_ledger.py` prints) and ingest of pushed receivers into the records file (B11). The batch record (B13) is the plan's batch entry, and no kit tool writes it.

The section also states how a supervisor asks the fleet's principal for an act (the line to type stands alone on the last line), that a refusal of an authorized step is reported and never routed around, and that an act only a receiver can do is submitted in that receiver's own session.

Gate 5.5, "Release Outcome Close-Out", is new and blocking. Before a migration's record takes a terminal status it requires a Release Outcome Report scored against `rubrics/RUBRIC_fleet_upgrade_outcome_v1.3.md`, two distinct issues (outcome and experience), and an eligibility receipt. No instrument writes that receipt yet; the procedure says to write it as a section of the outcome report.

Versions 1.10.1, 1.10.2 and 1.10.3 are corrections made after two rehearsals and one scratch build of a supervisor from the public template; 1.10.4 changes wording only. 1.10.5 corrects the procedure's statements about what the tools check, after an independent review, and says where `--only` is needed after a drop; it changes no tool. 1.10.6 changes steps B3, B8a, B9, B10 and B12 and the setup text for eight changes to the tools made after independent reviews; those changes have unit-test coverage and the later second outcome run exercised the worker path, returning FAIL accepted as R59 named limits. Versions 1.10.7 and 1.10.8 record the design pass and Round 2 corrections. The procedure's own changelog lists them.

### Grounded term display form (CAP-VOC-006)

In v3.35.1, `specs/AGET_VOCABULARY_SPEC.md` moved from v1.17.0 to v1.18.0. CAP-VOC-006 adds seven requirements for a highlighted term, meaning an inline code span that holds a term. A highlight holds an entry's preferred label, or an alternative label that points to exactly one entry, with spaces written as underscores and every other character unchanged (CAP-VOC-006-01). Single-word labels may be highlighted (CAP-VOC-006-02). A term with no entry in a named register must not appear in a highlight; a wanted term is written in italics (CAP-VOC-006-03). Resolution treats underscore and space as the same separator and does not fold letter case (CAP-VOC-006-04). The remaining three cover labels whose entries differ, choosing the most specific term, and plurals.

The existing prose rules (the self-disambiguation lines, the Marking Convention table, R-VOC-PROSE-001 and R-VOC-PROSE-003, CAP-VOC-002-03, CAP-VOC-004-02, V-VOCAB-009 and the compound-term regex) are now stated as governing the specification's own vocabulary register only. R-VOC-PROSE-002 is unchanged.

The specification declares V-VOCAB-011 to V-VOCAB-016. Four of them (011, 012, 013 and 016) are marked "automated (canonical check owed)": no check for them ships in this release.

The same file changes the `Aget_Instance` entry: its definition is rewritten, and its broader term moves from `Aget_AI_System` to `Aget_Agent`. The specification's v1.18.0 changelog entry does not list this change.

## Known limitations and disclosures

### Known gaps a supervisor may meet

From the statement above. Listed, not fixed in this release.

- A held file can leave a file the release marks as required unplaced while every kit check passes; read the receiver's own verdict.
- Replacing a held file needs the same option on two tools.
- The line-prefix setting exists only as an environment variable.
- A migrated member's instruction file may still name the old version on lines other than the version line. Seen on all three members of the live run: the specifications link kept the previous version, and no kit check reports it.
- The close-out step names an outcome rubric that the supervisor template does not ship; it is in the core repository. A supervisor built from the template has to read it from its clone of the core repository.
- A member with no workflow at its repository root reads as published with no continuous integration, whatever checks it runs elsewhere; the ledger does not examine them. Where a member with a root workflow has met the ledger's earlier conditions and its workflow checks could not be compared with its pre-migration revision (the revision was not found, or a workflow tree could not be read at either revision), the row reads INCONCLUSIVE with a reason saying so, unless a check-change ruling is recorded for that member. The ruling must be recorded under the name of the comparison it passes, `workflows-not-compared` (or `workflows-changed` for a changed workflow tree), and one under any other name passes nothing. The changed-tree check also admits a tightening review bound to that exact workflow tree with evidence. The ruling is a plain record; these classification checks do not authenticate its principal's line. The row's `checks_compared` value in the `--json` document says whether the comparison was made.
- A member name the register does not hold gives a Python traceback, not a message.
- Some tool help text and schema names still say v3.35.
- The session-rehearsal step chooses "the member with the most hooks" and gives no rule when no member has any.
- The prepare step writes one extra scope file that the procedure does not mention.
- The packet rehearsal's emulation of the version carriers sets `aget_version` in `.aget/version.json` to the target release number whatever it held; in `manifest.yaml` it changes the first field whose key ends in `version` and whose value begins with the previous release number, and in each extra carrier listed for the member the first unindented `canonical_version`, `aget_version` or `version` field whose value begins with it, and no other version field (in a listed extra carrier it also sets the first unindented `stamped` date, where present, to today). In the live run a manifest field holding a different, older value was left unchanged on the rehearsal copies while the rehearsal reported a pass; each member's own session later set it. The rehearsal does not reproduce every edit a member's session makes.
- The rules a typed line must meet (the prefix, a minimum length and, in the first batch list of the typed prompt that holds it, the batch's name; only a push line must also have the one fixed push form and equal the whole typed prompt it is found in, a pasted block among other words left out) are stated in a tool's documentation, not in one place in the procedure.
- The receiver watcher cannot wait for a turn end alone, and armed after a stop it waits for a change that has already happened.

### Gaps in the kit as shipped

Listed, not fixed in this release.

- **The second outcome test exercised 3.35.1 to 3.36.0 worker migrations and returned FAIL, accepted as named limits under weekly-train:R59. Real-fleet deployment is unverified.** The earlier rehearsals and first live run used 3.34.0 to 3.35.0 content; the second outcome run used 3.35.1 to 3.36.0 fixtures. The source and target versions are read from `.aget/migration_target.json`, but text naming the 3.35 release remains in 15 of the kit's 37 files. In seven of them it is in values a tool writes: schema names and the default receipt filename. ### Tool changes made after the live run

Eight changes to what the kit's tools do were made after independent reviews of the candidate. They have unit-test coverage; the second outcome run also exercised the worker path through apply, launch, push and the ledger, returning FAIL accepted as named limits under weekly-train:R59. Two of them, the push-line tests and the `--copy-root` folder tests, are described under "Authority checks: what the tools do and do not enforce". The others:

- **Every copy and clone the kit makes goes through one isolation routine.** It is in `scripts/migration_kit/copy_isolation.py` and is applied by the packet rehearsal (B2) and the repair rehearsal, the session rehearsal (B3) and the `--copy-root` launch, the suite check at the commit (B8a) and the after-run confirmation run. Before anything is removed, copied or cloned, the environment must hold no variable that tells git where a repository is (`GIT_DIR`, `GIT_INDEX_FILE` and the five others the routine names), and the folder to be filled must not be the member's own folder or a declared sibling's source folder, hold one or lie inside one; it is made inside a fresh run folder under a work root (see the work-root item below). After the copy or the clone (a clone is made with nothing checked out), and before any other git command, apply, hook or test in it, git run in the copy must name the copy as its working tree and the copy's own `.git` as its git folder and common folder: a copy that inherits a `core.worktree` setting, a `.git` file or link, or a `commondir` file is refused with nothing run in it, and so is one in whose `.git` folder an entry, such as `config`, is a symbolic link leading outside the copy. Every copy, a plain sibling folder included, is refused when any symbolic link in it, in the working tree or in `.git`, leads outside the run's folder (the copy, or the folder that holds the copy and its declared siblings); a clone, and the repair rehearsal's copy, is asked again after each checkout the kit makes in it, and the `--copy-root` launch asks again at each launch. Remotes defined by files under `.git/remotes/` or `.git/branches/` (an older form that `git remote` does not list and git still pushes to) are deleted. A copy of the member then loses its other remotes, and a clone of it gets a push URL that cannot resolve on each remote; each copied sibling folder that is a git repository keeps its remotes with such a push URL. The push URL git would use is read back after it is set, so a URL rewrite rule that redirects it is a refusal. That URL's scheme, `no-push`, is closed in each copy's own configuration: `protocol.no-push.allow = never` is written as the last entry of the copy's config file (so anything that file includes earlier, conditionally or not, is overridden) and read back as git will use it. A copy is refused when the environment reopens the scheme (a `GIT_ALLOW_PROTOCOL` naming it, or configuration given through the environment), or when configuration git reads after the copy's own file (a worktree configuration, or configuration from the environment or the command line) includes another file. A copy is also refused when any git configuration it reads (the member's own, global or system) holds a conditional include whose condition can change after isolation (`onbranch:` or `hasconfig:`), or an include of a file inside the repository, since a checkout or a configuration change could make either redirect a remote later. An operator whose global or system git configuration uses such an include is refused until it is moved out of that file for the run or given a `gitdir:` condition; the refusal names the file and the entry. Unconditional and `gitdir:` includes of files outside the repository are kept: they are in force when the routes are read. After each checkout the kit makes in a copy, the push routes are read again. Only that scheme is closed: a copy's other transports are left as they were. Each kit function that changes a repository's remotes or configuration (removing remotes or URL rewrites, setting the dead push URL, closing the scheme, and the short-lived remote the push-route reader adds to resolve a destination) checks for itself that it was given a run folder, that the repository lies inside it, and that git names the repository as its own working tree with no entry of its git folder linked outside it and everything reachable in its git folder is a folder or a regular file with one name: a second name (a hard link: git appends a reflog in place, so the file behind the other name would change), a FIFO, socket or device, and any entry or folder that cannot be inspected each refuse; symbolic links that stay inside the copy are followed to the file or folder they name, wherever it lies, each folder once, and only a link whose target does not exist is skipped; otherwise it refuses before any git act. There is no exemption, the object store included: a repository that shares object files by hard link, as a plain local `git clone` makes, is refused. Every copy and clone the kit makes has its own files. Before each checkout, add, rm or commit the kit makes in a copy after member code has run there, it asks the same identity test and LINKS again. Every git command line the kit's tools build to read a live member takes no optional lock and fetches no missing object (a read that would need a missing object reads nothing); the reads made through the kit's shared read helper, every `diff` read among them, are also given a private copy of the index, so a stat refresh never rewrites the member's. A test lists every git command line in the kit and requires one of these, or a named reason it is not a member read (an act in a copy or clone the kit made, or a read of a framework repository). A copy of a member that has no `.git` of its own (a member that is a folder inside a shared repository) is refused with nothing run in it: git run in it would act on the shared repository. A sibling folder with no `.git` at its top is copied as it is and only the link test is asked of it, and git run in its copy acts on whatever repository encloses the copy folder. Not closed: a repository nested deeper inside a copied sibling, a symbolic link that code running in the copy makes after the link test, a submodule, a branch whose remote is a path with no remote section, a remote added during the run, a push to an explicit URL or path, the object store's `alternates` file, hooks, and what code does after it starts. A hook that the member installed as a symbolic link into its own tree (such as `.git/hooks/pre-commit -> ../../scripts/pre-commit`) is admitted, and git runs it through the link whenever it runs the copy's hooks. A hook link leading outside the run's folder makes its copy refused like any other such link: at B2 that member reads `REFUSED` and the other members are still rehearsed. Such a member is dropped from the batch, or its hook is changed by the principal's line in that receiver's own session (procedure B2), never by the kit or the supervisor. No tool refuses an output or evidence folder (`--evidence`, `--out`, `--receipt-dir`) placed inside a member's repository or inside a repository that holds a member: keep them outside (operator rule). `--scratch` is a work root and is refused there.
- **A protected file is replaced only when it is byte for byte an upstream version.** `prepare_batch.py` classifies a protected payload file; `prepare_launch.py` skips protected paths and applies the same rule to an unprotected payload file. Either class is `write-upstream` (replaced) when it differs from both release tags but its bytes equal one version of that path at some tag of a local template clone or core. A path with no release source is a `hold` of kind `no-source`, kept the same way. A payload path that is or goes through a link, or resolves outside the member, is `unsafe` in both the protected-write list and the launch packet: never written, the member's session told to leave it, and the after-run check INCONCLUSIVE, so the member is not pushed with that path unmigrated. A member's session places its release files with the packet's sealed placer (`python3 <packet root>/stage/kit/place_file.py ...`, the same act), not with `cp -f` and `mkdir -p`. Evidence and output files the tools write into the folders you name (`--evidence`, `--out`, `--receipt-dir`, `--scratch`; for example `baseline_record.json`) are not written by the contained writer and can follow a link there: keep those folders outside every member and free of links (operator rule). Stated limits: see "What the kit guarantees, and its stated limits".

Where git lists several names one per line and they cannot be told apart (with `GIT_CONFIG_GLOBAL` unset and a line feed in `HOME` or `XDG_CONFIG_HOME`), that element cannot be read. The configuration files read include every file an `include.path` or `includeIf.<condition>.path` names, resolved as git resolves it (its `~` forms expanded by git, a relative name taken from the including file's folder), whether or not it holds a setting; a file named by an include whose condition does not hold is read too, so a change to it also reads INCONCLUSIVE. This holds for an include set by the process's own configuration (`GIT_CONFIG_COUNT`, `-c`) as well as one in a file, and a configuration entry from any other source the kit cannot read makes the reading unavailable (INCONCLUSIVE); no entry is passed over. These configuration queries describe what ordinary git commands read: `GIT_CONFIG`, which only `git config` honours, is not passed to them. Any difference, or any of these that cannot be read (at either reading, or at both), reads INCONCLUSIVE naming it, in the judged run and in the packet rehearsal's reference run alike. The pre-push hook run here is the file `hooks/pre-push` in the member's git common folder: a hook that a `core.hooksPath` setting names is not run at this step, and where no file is at that place the record says `hook.present: false` and PASS needs only the suite (where one is there and `core.hooksPath` names another, the file at the default place is the one run). The hook is placed in the clone as a regular file before it runs, chosen by where its entry resolves with every link on the way followed (the hooks folder itself included), and the git folder's name is read byte for byte: a file in the member's git folder, its bytes; a file in the member's working tree, the bytes of the same path in the clone, at the tested commit. An entry that resolves outside the member, or to a path the tested commit does not have, is not run, and the record reads INCONCLUSIVE with `hook.present` true, `hook.run` false and the reason in `hook.why`, never PASS without the hook. A hook still running when the suite's time limit (2400 seconds) runs out has its process group killed and reads INCONCLUSIVE. The B8a record keeps whether a hook was present, its exit and the last 600 characters of its output, or why it was not run; it does not keep the hook's source entry, where that entry leads, the path it was placed at or its digest. The push at B10 is a plain `git push`, which runs the hook git finds. Each copied sibling folder that is a git repository goes through the same isolation as the clone before it is checked out, cleaned or used: git run in it must act on the copy, and each of its remotes gets a push URL that cannot resolve. When the suite ran to its end without moving HEAD, the record keeps the status lines (the first 40 of each reading, with its count) and what was allowed. Not read as a change: a file git ignores, an untracked file under a `__pycache__` or `.pytest_cache` folder, a change made and undone between two readings, an empty folder added or removed, times and owners, any other change inside a `.git` folder, a write by a process that outlives the suite or the hook outside its process group, a change inside a copied sibling beside the clone, anything written outside the clone, and a ref moved while HEAD and the status lines stay as they were (a stash, a new branch). A member whose suite or hook leaves a tracked file changed, or a new file that `git status` lists outside those cache folders, therefore reads INCONCLUSIVE until `--allow-path` names the path. The packet rehearsal's reference run (B2) calls the same function without the option: there only HEAD and the ignore state are judged, and the rehearsal keeps none of the status readings in its own output.
- **The ledger (B12) no longer reads an uncompared workflow as unchanged.** A member with a root workflow whose workflow checks could not be compared with its pre-migration revision (revision not found, or a workflow tree unreadable at either revision), and whose row no earlier ledger condition has already settled, reads INCONCLUSIVE with a reason saying so, unless a check-change ruling is recorded for that member in the shape `record_authority.py` writes (a named check with its change and the principal's line; a value written by hand in another shape is read as no ruling); the ruling must be recorded under the name of the comparison it passes, `workflows-not-compared` (or `workflows-changed` for a changed workflow tree), and one under any other name passes nothing. A shared root's `covered: false` for a member counts only with its source and the principal's line beside it. Each row carries whether the comparison was made (empty for an excluded member, an unavailable one, or one whose published version is below the target). Not compared: a workflow change made in a commit before the one that changed the version file, and files a workflow uses outside the workflow folder. Whether a member has a root workflow is read from its local checkout. See the item on a member's workflow under "Known gaps a supervisor may meet".

### What the kit guarantees, and its stated limits

Written from the kit's source after its design pass. Four rules apply at every site of their class: R1 containment
(where an act may happen), R2 result binding (which results count), R3 instruction fidelity (what a session is told,
permitted and judged on) and R4 all-or-nothing apply (what a failure leaves). The items below are what they do not
close. They are limits of this release, not defects to report.

- **One condition for every guarantee about a member's files: nothing else changes that member's folder tree while a
  kit step works on it.** No other process, not only no second kit run, may write, rename or move anything in it. The
  contained writer opens each folder again and compares it immediately before each act, which narrows the window and
  does not close it: a folder moved after that last check is not seen, and the write can land in the moved folder. The condition and its guarantee cover the member's own files: the packet root, the records, the baselines and the census output outside the member carry no such guarantee.
- **A session's own writes are detected, not prevented.** For the files a member's session writes with its edit tool
  and the git commands it runs, the kit checks every granted path before it grants it and again immediately before the
  session starts, and the after-run check G then reads every path the transcript shows written, every path git shows changed or untracked, every path already changed before the run, and every `.claude/` file whose bytes changed, ignored by git or not: a path that goes
  through a link, is not a regular file, or has a second name reads FAIL, so B9 holds the push, and so does a link
  under `sessions/`, a change to the packet's sealed stage, or a change to the member's sealed baseline. G cannot undo
  a write that went through a link, and it does not see a link made, written through and removed inside the session, nor a write to a path git ignores outside `.claude/` that no edit-tool call names.
- **What member code writes is not contained.** Suites, tests, hooks, the packet auditor and the sessions' own allowed
  commands can write to absolute paths and the home folder. Only an operating-system sandbox would stop that, and this
  release has none. The after-run check measures inside the member, and B8a inside its clone. A process that member code starts outside the run's process group, or one a kill fails to stop, is not reached by the kit's time limits and can go on writing after the kit has read its result; the contained environment the kit gives a run holds only while member code does not change it.
- **The packet's seal is a mode bit.** The same operating-system user can make the stage writable again. Every launch
  and every after-run check compares the stage with its manifest, which detects a change and does not prevent one.
- **The contained writer needs its host's support.** It refuses, and never writes unprotected, on a host whose Python
  lacks folder-relative open, rename, folder, delete and remove calls, `O_NOFOLLOW`, `O_DIRECTORY`, or an rmtree that
  does not follow links. A file that has a second name inside the member, on purpose, is refused as a write target
  too, with a reason.
- **A result is bound to its run, not authenticated.** `runs.jsonl` and every result file are plain files: anyone who
  can write them can forge a row. A run that dies before its first act (the interpreter or an import fails), or that
  cannot append to its run log, leaves no record, and an earlier result for that output stays current: read each
  tool's exit. A run that writes to another output path does not replace this one.
- **The receipt form is strict and new.** A receipt counts only when the section headed exactly `## Attempt <attempt>`
  for the packet's attempt is its last and ends with exactly one line `Terminal: <value>`, the value one of ACCEPTED,
  BEHAVIOUR_VERIFIED, REJECTED or CANNOT-RUN, and only the first two are a success. None of the 32 receipts the
  previous migration produced has that line, so a receipt in the older forms reads INCONCLUSIVE at the after-run
  check, NOT PUSHED at B10 and RECEIPT-NOT-SUCCESS at the ledger: this fails closed and costs a repair attempt. The
  ledger's route that ingests a terminal from the producer's state file carries no receipt path, so there the
  terminal is judged by its exact value only.
- **Instruction fidelity bounds a session; it does not make it comply.** The quality of a merge is not judged: only
  that every line of the member's own survives. The difference a KEEP item asks the session to record is not checked:
  no tool reads the receipt for it. Meanings are fixed when the packet is prepared, so a file edited between preparation
  and launch reads as changed. No kit step runs `verify_extension_survival.py --verify` after a migration: preservation of a
  member's own extensions is read back only for payload items (KEEP unchanged, every line of a MERGE surviving), not
  for the extension record that tool keeps.
- **All or nothing, per member, for the kit's own writes.** "Nothing changed" is claimed only for REFUSED.
  ROLLBACK-INCOMPLETE and a killed run (IN-PROGRESS) report a partial state; there is no journal, recovery is by hand
  (the list's digests name every target), and nothing is claimed per file across a power loss. Catchable interrupts
  are handled in the apply only; a rehearsal or launch that is interrupted leaves its result not finished. A rollback
  restores bytes and permission bits, not times, owners or extended attributes. A launched session's own writes are
  outside this rule. A refused rehearsal copy is not restored: nothing more runs in it and its verdict is never PASS.
- **No git transport inside a session.** A member's sessions (baseline and migration) run with git's protocol
  allow-list set to the empty value (`GIT_ALLOW_PROTOCOL=` with nothing after it), so git starts no transport,
  a remote helper included, and a push by git from a session fails whatever form its destination takes. Not
  closed: code in the session that removes or changes that variable before it runs git, and a write to a remote
  by any means other than git. The cost: a member's test that
  clones, fetches or pushes, even to a local path, fails inside its sessions. It fails in the baseline session too, so
  the after-run check does not count it as new; the suite check at the commit (B8a) runs outside the sessions.
- **Push routes from a copy are closed by what git itself would resolve.** Isolation removes URL rewrite rules copied
  into a copy's own configuration, then asks git for every route it could push by (each remote, each older-form remote
  file, every rewrite rule's value, `remote.pushDefault`), each resolved as git would resolve it for a push (a
  `pushInsteadOf` rule included), and refuses the copy if any resolves to anything but the
  kit's push URL that cannot resolve, whose scheme is closed in the copy (above). This is a check at points in
  time: the routes are read at isolation and again after each checkout the kit makes in the copy. A change that
  code running in the copy makes afterwards (to HEAD or to configuration), and a change another process makes to
  an included file outside the copy (the exclusive-mutation condition), are not closed.
  B1 records each member's push destination as git resolves it, and B10 refuses a member whose destination differs.
- **The kit's git acts and member code in copies run in a contained environment.** The checkouts and commits
  the kit makes in a copy (the repair and packet rehearsals, the suite check at the commit, the confirmation run)
  run with no git transport and with no hook the copy carries (core.hooksPath is pointed at an empty folder). A
  member's suite run in a copy by those tools runs with git bounded by the folder that holds the copy
  (`GIT_CEILING_DIRECTORIES`), with no system or operator git configuration (a minimal one in that folder), and
  with `CLAUDE_PROJECT_DIR` set to the copy; its own transports are left as they are, so its local clone, fetch
  and push tests still run. Before each such run or act, the copy's push routes are read again under that
  environment, and a route that no longer resolves to the closed dead scheme stops it (the suite is not run,
  the act is not made). Not closed: code in the copy that changes this environment for itself.
- **Each run's copies and clones go into a fresh run folder under a work root.** The packet, repair and
  session rehearsals use the `--scratch` folder you name as the work root; the suite check at the commit uses
  `~/.cache/aget-suite-at-commit/` (its reference run, the `reference/` folder there); the after-run
  confirmation run uses `<packet folder>/<release>/runs/` (or `AGET_MIGRATION_WORK`). A work root
  inside any git repository, or one that is, holds or lies inside a member, a declared sibling's source folder
  or the framework root, is refused before anything is made, and so is one for which git cannot answer
  whether it lies in a repository (a malformed git configuration, for example). Each run makes its own folder
  in it and nothing is removed to make room, so two runs never share a folder and no run clears another's. A
  receiver's name must be a single folder name (not a path, `.` or `..`): any other is refused before an
  evidence, run or copy folder is made for it, and each copy and clone is checked to lie inside its run folder
  before it is made. Run folders are kept; removing old ones is yours. The packet and repair rehearsals' results name their run folder; the session rehearsal's result does not. Evidence still goes to
  `<--scratch>/evidence`.
- **Rehearsal sessions, B8a's hook and the known-missing auditor run inside the run.** The session
  rehearsal's sessions run in the contained environment above with the copy's own hooks in force and no git
  transport; every symbolic link under the run folder (the copy and its declared copied siblings, their git and
  hook folders included) must resolve inside it at the launch and again after the session, and one that no
  longer does makes the after-run result INCONCLUSIVE; with declared siblings (those given to the check and those in the packet's row for the member, one population that F's confirmation run also copies) the check walks the folder that
  holds the copy and all of them, and a narrower folder is not accepted. A `core.hooksPath` that names a folder
  outside the run folder, or holds a link leading outside it, refuses the launch; it is read again (under the
  session's configuration, its value byte for byte) after the session, and one that now does, or cannot be
  read, makes the after-run result INCONCLUSIVE. B8a's pre-push hook
  runs as a regular file in the clone (the B8a item). The known-missing auditor the packet rehearsal runs must
  resolve to a file inside the copy's run folder or the kit, and runs in the contained environment; any other
  path is refused and not run.
- **Ignore state is detection, with stated gaps.** The same ignore-state reading is taken around the packet
  and repair rehearsals' suites, the known-missing auditor and the after-run check's confirmation run (F): a
  difference makes that result not count (INCONCLUSIVE, naming the element). The pre-launch `--snapshot` records
  the live member's ignore state (the user's real global configuration is read, never written) and the paths
  git ignores; for a rehearsal copy (`--copy-run`, which the session rehearsal now passes to the snapshot too)
  also under the contained environment its session runs under. After the session E compares them, and a
  difference is INCONCLUSIVE naming the element. Because every configuration file git reads is part of the
  state, a run or session that writes the repository's own `config` reads INCONCLUSIVE as well. The one
  exception is a `.gitignore` at a path the step writes (a protected file the apply wrote, or a write-set path,
  such as a track-skills receiver's `.gitignore`): it is recorded, and every path git ignores after the run and
  did not before must then lie in the write set, else it is an E finding. Not seen: a write into a path that
  rules already in force before the run ignore (outside `.claude/`, which E reads whole), and an ignore rule
  changed and restored between two readings. In a live member, a change to the user's global ignore or
  configuration file by an unrelated process during the session reads INCONCLUSIVE, a conservative false alarm. These readings compare files. Configuration given only to a process (environment variables such as `GIT_CONFIG_COUNT`, or `-c`) is not a file and is not compared, so each reading assumes the caller's process configuration is the same at every checkpoint; an `onbranch:` include whose activation changes while all five elements read the same is not seen; changed rules in a `.gitignore` that the index holds and the working tree does not, with equal index flags, may go unseen; and the index git selects is compared by its path name, not by its identity or by content beyond its flags.
- **A protected-write entry acts only at its member.** `apply_protected.py` and its trial run refuse an entry
  (REFUSED, `NOT A MEMBER LOCATION`, nothing written) unless its location is the location the fleet register
  (`.aget/fleet/FLEET_STATE.yaml` in the kit's repository, read as it stands) records for that Aget, links
  resolved and `~` not expanded, or lies inside the run folder a rehearsal names with the new option `--run`. A
  register that cannot be read, or lists the Aget other than once, refuses a location outside `--run`; a
  location inside `--run` is admitted as a copy without requiring the register to resolve (BIND does not authenticate a
  copy); a `--run` folder that holds the
  Aget's register location is refused, so it cannot admit the live member as a copy. The three rehearsals pass
  their run folder.

  - The ignore-state reading is unavailable, and the result INCONCLUSIVE, when a configuration file git names is not a regular file (`GIT_CONFIG_GLOBAL=/dev/null`, for example), or when, with `GIT_CONFIG_GLOBAL` unset, `HOME` or `XDG_CONFIG_HOME` holds a line feed: point the setting at a regular file for the run.
  - Two committed workflows that share a display name read CI-INCOMPLETE at the ledger, not proven, since a run cannot be matched to each: give each workflow its own name.

### Authority checks: what the tools do and do not enforce

Read from the kit's source at the release candidate. The items say what the tools check and what they do not; the limits listed are not fixed in this release. Where a rule for the operator is given, it is an operator rule, not enforced by the tool.

- **A launch with `--copy-root` checks no typed line.** `launch_batch.py --launch` without `--copy-root` checks the recorded typed authority and exits 6 without it. With `--copy-root <dir>` it runs no authority check. It refuses the folder (exit 2, reason printed) unless `git remote` prints nothing there, the folder is apart from the member's own folder (not the same folder, not inside it, not containing it, and not sharing its `.git` through a link), git run in it names the folder as its working tree and the folder's own `.git` as its git folder and common folder, its `.git` folder holds the marker file that `rehearse_v37.py` writes into each copy it makes, naming the digest of the packet file's bytes and the member, and its HEAD equals the packet's HEAD for that member. The git test asks git itself, with the environment the session gets: a copy whose `core.worktree` setting names the member (git commands in such a copy change the member's files), a linked worktree, a `commondir` file and a bare repository are refused, and so is an environment that holds `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES` or `GIT_NAMESPACE`; the object store's `alternates` file and hooks are not read. `rehearse_v37.py` refuses, before it removes or copies anything, a copy folder that is the member's own folder, holds it or lies inside it, and makes the same git test on the copy before it runs any other git command there, applies the list or launches. This does not prove the folder is a throwaway copy: the marker is a plain file, and anyone able to write it can forge it in another folder that has no remote and is at the packet's HEAD. The session rule `Bash(python3 scripts/migration_kit/launch_batch.py:*)` covers the command with any arguments. The procedure uses `--copy-root` only inside the session rehearsal (B3). Restricting it to rehearsals is an operator rule, not enforced by the tool.
- **The rules-file test looks for a call, not for every path.** `tests/migration_kit/test_migration_kit_batch_rules.py` passes when each ruled tool's source holds a call to the authority check. It does not test that every path through the tool makes that call.
- **A launch line need not name the launch.** In addition to the provenance, prefix, length and batch checks, the recorded line must not match the tool's recognized launch-exclusion pattern. Only a push must be named.
- **The launch check binds the batch's name; the push check binds the packet.** When the launch tool calls the check, it passes the packet's `batch` value and nothing else of the packet, so another packet file with the same `batch` value passes the launch check on the same recorded line, whatever receivers it lists; launching with the packet that was prepared and rehearsed for that batch is an operator rule, not enforced by the tool. A push line is recorded for one packet file (`record_authority.py --act push --packet`, which refuses without `--packet` and keeps that file's digest with the line), and `push_batch.py --push` refuses a push from any other packet file, even one with the same `batch` value.
- **A push line is tested for its form, not for its meaning.** A push reads only a line recorded for the push (the entry keyed `<batch>:push`, written by `record_authority.py --act push`); the batch's launch line is never push authority, and with no push entry `push_batch.py --push` exits 6. The push line must have one fixed form: the prefix, then `push the commits of batch N`, optionally more batches (`batches 10t and 10`) and ` with commit SHA` (or `commits SHA, SHA and SHA`, each 7 to 40 hexadecimal characters), and nothing else. With the default prefix: `GO supervisor - push the commits of batch 1`, or `GO supervisor - push the commits of batch 12 with commit abc1234`. Runs of whitespace are not compared, and after the prefix letter case is not compared either; the prefix itself keeps its letter case (`go supervisor - ...` is refused). Every other line is refused, and the reason states the form: "the push is not approved yet", "hold the push until I review", "the push remains unapproved", "the push is prohibited", "the push is held" and "push tomorrow" are refused. An affirmative line worded another way ("batch 1, push the verified commits", "no problem, push it") is refused too, and the principal types the form. A commit the line names requires a matching `--extra-commit`, the shorter id a prefix of the longer; when HEAD moved since the launch check, the extra-commit route compares HEAD with the longer id; with HEAD unchanged, a supplied extra commit does not change the checked commit the gate permits; a push whose line names a commit is refused when no `--extra-commit` is given.
- **For a launch, the prefix, length and exclusion tests read the line as recorded, not the whole typed prompt.** The tool looks for the recorded line as part of a typed prompt. The batch test reads the first batch list in that prompt, leaving out a pasted block that sits among other words; for a launch the prefix, length and exclusion tests do not read the prompt, so a recorded launch line is not refused by them although the typed prompt went on with other words. For a push line, and for a baseline-equal ruling line, the newest prompt that holds the line must equal it once runs of whitespace are collapsed: a recorded "... push the commits of batch 1" is refused when that prompt went on "... tomorrow, not today". A pasted block that sits among other words is left out of that comparison, so a condition that exists only inside such a block is not seen.
- **Operator rule for a push.** The tool requires a dedicated push line in the fixed form and compares it with the whole typed prompt. Not enforced by the tool: that nothing is recorded as push authority when the principal withholds or conditions the push where the tool does not read it. The tool does not read a condition that exists only inside a pasted block beside the line, or a later prompt that withdraws the push without quoting the line.
- **A dropped member is still launched from an unchanged packet unless `--only` leaves it out.** `prepare_write_list.py --drop` marks a member blocked in the write list only. The apply step skips a blocked member, with or without `--only`. The launcher reads the packet and never the list, so a dropped member is still launched (in a packet prepared with `--placed-by-apply`, as the procedure's B1 prepares it, a migrating member gets a baseline session and a migration session, told its files were already placed and to set the version and commit) unless the packet is rebuilt without it or the remaining members are named with `--only` at every launch. The push tool does not read the list either: it refuses a member that has no launch evidence, so a dropped member that was never launched is not pushed, and one that was launched by mistake is not held back by the drop.
- **Two push options are compared with no typed line.** `--extra-paths` and `--allow-dirty` on `push_batch.py` come from the command line alone; no typed line is compared. `--extra-commit` must be a commit the recorded push line names (` with commit SHA`, the shorter id a prefix of the longer). Using them only when the principal's line names them is an operator rule, not enforced by the tool.
- **A baseline-equal ruling is not tested for its meaning.** A ruling that a failing suite equals its baseline is accepted when the recorded line is found typed in the session's records and has one fixed form: the prefix, then `the failures at SHA are baseline-equal`, SHA being 7 to 40 characters the commit's id starts with (for example `GO supervisor - the failures at abc1234 are baseline-equal`). The newest prompt in the session's records that holds the line must equal it once runs of whitespace are collapsed (a pasted block among other words is left out of the comparison). Every line in another form is refused: "do not treat abc1234 as baseline-equal", "abc1234 baseline ruling remains unapproved", and an affirmative ruling worded another way ("same failures as before"). This is a test of form, not a reading of meaning. The line does not name the member. The ruling file, the baseline record, the after-run verdict and the suite record that the push gate reads are plain files in the evidence folder; their origin is not checked. Recording a ruling only when the principal affirmed it is an operator rule, not enforced by the tool.
- **Messages the tools print can claim more than the tools check.** Some help texts, printed messages and generated receiver prompts in the kit still state stronger authorization or copy guarantees than the tools establish: a launch prompt says the session was launched on the principal's authorization even on the unchecked `--copy-root` route, the push options' help says a value was named or allowed in the principal's line although nothing compares them, and the `--copy-root` help calls the folder a throwaway copy without proving it. These strings are unchanged in this release. They are not evidence of authorization.
- **Exit code 0 is not a pass.** A live launch of the members' sessions (B8) exits 0 whatever its after-run checks said. `push_batch.py` prints NOT PUSHED for a receiver its gate refuses and does not raise its exit code for it: a run in which the gate refuses every receiver exits 0, and a push that ran and was not confirmed makes the exit code 1. Read the printed verdict for each member.
