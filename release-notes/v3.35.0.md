# AGET v3.35.0 — Receiver correctness

Release candidate prepared 2026-09-25 for publication on 2026-09-26. This document does not assert publication, installation or downstream acceptance.

## What changes

Each change in this release fixes something a receiving Aget runs or reads. The release carries three outcomes, one deprecation removal and two editorial cleanups.

| Outcome | Change | Shipped entry point |
|---|---|---|
| M-3.35-1: Proposed actions say what they move | Each proposed action is tagged as moving the outcome or only its measurement. Gated outcome steps are surfaced as decisions. The deferral scan reads handoff documents on disk, from configurable locations, and reports four distinct results. | `scripts/propose_actions_handoff_scan.py`, `scripts/propose_actions_classify.py`, `/aget-propose-actions` v1.9.0 |
| M-3.35-2: CI host independence (advisory) | A test's outcome must not depend, undeclared, on anything outside the repository checkout. Declare the precondition and skip; never weaken the assertion. Establish hermeticity by execution. | `specs/AGET_CI_SPEC.md` v1.5.0, CAP-CI-010 |
| M-3.35-3: The strict close gate runs in template-created Agets | All 13 templates carry the lifecycle module and the specification the gate reads, and the close-project skill passes the arguments the gate requires. | `scripts/close_gate_lifecycle.py`, `specs/AGET_PROJECT_PLAN_SPEC.md`, `/aget-close-project` |

### M-3.35-1: Proposed actions say what they move

A funded batch of proposed actions could close without the one gated act that would have moved its outcome, because nothing distinguished an action that changes the outcome from one that only improves how it is measured. `/aget-propose-actions` v1.9.0 adds a `Moves` column to its proposal table and a close report that states outcome and measurement separately. A gated outcome step is listed as a decision for the principal, not silently dropped. `scripts/propose_actions_classify.py --check-outcome-gating` checks a batch for this.

The deferral scan decides whether a recent handoff document already parked a candidate's subject. Earlier versions scanned only `docs/`, and the two selector forms in use were wrong in opposite directions: file modification time made every handoff in a fresh clone look recent, and commit history could not see an untracked handoff. `scripts/propose_actions_handoff_scan.py` scans committed handoffs by authored date, plus untracked and locally modified ones. Its locations come from an argument, then `.aget/config.json` (`propose_actions.handoff_locations`), then the default `docs`, `planning` and `inbox/outbound`; the release-class `handoffs/` directory is excluded. It reports `MATCHED` (exit 1), `NONE-MATCHED` (exit 0), `NO-CANDIDATES` (exit 0) or `UNAVAILABLE` (exit 2). `UNAVAILABLE` means the scan could not look, and it is never reported as a clean scan.

This outcome passed two rounds of independent review. The first round found seven material defects; all were fixed before landing, with regression tests.

### M-3.35-2: CI host independence (advisory)

CAP-CI-001 governs what a test imports. Nothing governed what a test reaches: the filesystem beyond the checkout, or a resource obtained through a child process. A test could satisfy test isolation and still be unable to pass on any runner. CAP-CI-010 adds three advisory requirements. Undeclared dependence on a resource outside the repository checkout is prohibited (CAP-CI-010-01). A test that depends on a resource that may be absent declares the precondition and skips, and never weakens the assertion (CAP-CI-010-02). Hermeticity is established by execution in a distinct environment, not by reading sources (CAP-CI-010-03). The specification moves to v1.5.0 and declares V-CI-009 to V-CI-011.

It is advisory on purpose. A blocking check for this class was drafted and measured against five test files verified correct by inspection: five false positives, zero true findings. The rule was authored on 2026-09-22 and landed on the release branch on 2026-09-24 as `333bf2b`, a cherry-pick of `8c951f2`.

`tests/test_ci_host_independence.py` partly implements V-CI-011 for CAP-CI-010-03. It verifies that the CI workflow runs the whole suite as an unconditional, blocking step on push and pull request, on a GitHub-hosted runner, from a fresh checkout of this repository, and that a run inside GitHub Actions reports itself as GitHub-hosted. It does not verify the third part of V-CI-011, that a claim of hermeticity waits for that run: nothing machine-readable records such a claim yet, so that part is tracked for a later release. CAP-CI-010-01 and CAP-CI-010-02 remain inspection checks; an inspection at this release found tests that depend on the host's shared temporary directory, on a linter being on the path, and on host git configuration. Both inspection checks, V-CI-009 and V-CI-010, therefore fail at this release (advisory, not blocking), and two tests weaken an assertion instead of skipping. Recorded for the next release.

### M-3.35-3: The strict close gate runs in template-created Agets

The v3.34.0 tags of all 13 templates ship `scripts/close_gate_check.py`, which imports `scripts/close_gate_lifecycle.py` at module scope, without that module. In an Aget created from a template, the strict close gate therefore stopped with a module-not-found error before evaluating anything. The gate also reads `specs/AGET_PROJECT_PLAN_SPEC.md`, and the templates' `/aget-close-project` skill invoked it without the `--phase` and `--disposition` arguments it requires.

All 13 templates now carry `scripts/close_gate_lifecycle.py` and `specs/AGET_PROJECT_PLAN_SPEC.md` next to `scripts/close_gate_check.py`, byte-identical to the core repository. The framework's `/aget-close-project` skill replaces each template's copy. Each template was checked by running its own gate on fixture plans, in both the entry and the exit phase. The claim is that the gate runs. It is not a claim that the gate catches every unfinished row; see Known limitations.

## Repairs that had not shipped before

The shipped `scripts/propose_actions_classify.py` is the framework producer's tested copy. Besides the outcome-gating check, it carries four earlier fixes that the producer had applied only to its own copy and never shipped:
- `author` matches only its verb forms, and `record` preceded by a determiner (of record, the record, a record) is read as a noun, so neither word misclassifies an audit action as synthesis;
- actions are grouped by a declared subject as well as by artifact path;
- coverage (`COVERED`, `NO_SUBJECT`, `NONE_GOVERNED`) is reported separately from the pairing verdict, so a pass over nothing examined is visible;
- the stem `populat` matches only `populate`, `populates`, `populated` and `populating`, so the noun "population" no longer counts as a synthesis action.

## Removals

### DEP-BASENAME-VPP-001: the script name `scripts/validate_project_plan.py`

Deprecated in 3.32.0, the release that first shipped the public registry `governance/DEPRECATIONS.md`. The grace period was satisfied: marked in 3.32.0, carried in 3.33, removable from 3.34.0, removed in 3.35.0. Only the name was deprecated, because one basename had two referents that answer opposite questions. No shipped repository carried the delegating shim, neither the core repository nor any template, so no receiver loses a file. Migration: for plan conformance use `verification/validate_project_plan.py <path> --strict` from a clone of the core repository; the templates do not ship it. The execution-authorization gate (`scripts/validate_execution_authorization.py`) is producer-internal and is not shipped by the framework or any template. A citation of the bare basename, without a directory, is ambiguous and should be re-cited with its path. This removal is not a breaking change.

### A retired release-closure requirement

The producer's release procedure had required a five-row behavioural-verification matrix before a 3.31 release project could close. Its closure force was withdrawn on 2026-08-29. It was carried through two minor releases and is removed in 3.35.0 as scheduled: it is no longer a closure gate for any release project. Its historical results, including failed rows, are archived, not erased; a deprecation is not a pass. The matrix was never part of the shipped framework, so receivers have nothing to change.

## Known limitations and disclosures

### The close gate runs; it is not a complete check

The gate's test for an unfinished status row is a list of unfinished words. A row whose status is an unlisted word, such as `NOT RULED`, `HELD` or `AWAITING`, reads as finished, and a close can pass over it. The gate's release-class guard runs only where an Aget carries `scripts/release_close_guard.py`, which the framework does not ship, so the gate skips that check. Neither is changed by this release. Both are tracked for a later release.

### Citations the close-project skill cannot resolve

The `/aget-close-project` skill copied into the 13 templates cites four requirement IDs (`CAP-PRJ-001`, `CAP-PRJ-002`, `CAP-PRJ-004`, `CAP-PRJ-007`) and two tests (`tests/test_close_gate_value_resolution.py`, `tests/test_close_project_index_regeneration.py`) that the framework does not ship. It also carries internal project and tracker references, some of which earlier template copies already carried. Its Step 9 calls `scripts/generate_project_plan_index.py`, which the framework does not ship; that step runs only when `planning/INDEX_PROJECT_PLANS.md` exists, and no template has that file. None of these affects the gate's verdict. They are tracked for the next release.

### Tagging route and carried test failures

The producer's automated tagging tool runs a pre-tag test battery that has no way to carry known failures. Four traceability tests in the producer's own suite fail on every run. The producer's CI and pre-push checks deselect exactly those four by name, but the tagging battery cannot, so the tool refuses. As with 3.34.0, this release is tagged by the documented manual procedure. The four failures are carried as reported debt, not counted as passing. A fix to the battery is recorded for the next release. The battery also carries one named check that fails: citation resolution, with 490 citations in shipped files that do not resolve inside the framework. 471 are lesson citations (468 in skills, 3 in the changelog), which cite lessons held outside the public repositories. The other 19 name scripts or specifications the framework does not ship: 14 in skills, and 5 in this release's changelog and handoff that name a script only to say it is not shipped or was removed. They are citations only and do not change any script's behaviour. Recorded for the next release.

### Receiver-contract test

`tests/test_close_gate_receiver_contract.py` now checks each digest in the 3.31.1 delivered-files manifest against that file's bytes at the manifest's `source_ref` tag, and checks that the manifest equals its own copy at that tag. Before this change, this release's editorial edit to `specs/AGET_PROJECT_PLAN_SPEC.md` made the test fail, although the 3.31.1 manifest is correct for 3.31.1. Without the tag, the test skips and names the missing precondition. The exception is the core repository's CI, which fetches tags and fails if the tag is missing.

### Host-dependent tests in the framework's own suite

With the host's default temporary directory, 8 study-topic tests in the framework's own suite fail when stray directory trees shaped like a portfolio checkout exist there. With an isolated temporary directory, the full suite passes. The tests do not yet declare that precondition. Known issue, tracked.

### Deployment specification publication state

`DEPLOYMENT_SPEC_v3.35.0.yaml` records `status: prepared` at the tag and is not edited afterwards. The release procedure's step that changes the field to `released` after tagging cannot be met as written, because its check reads the immutable tagged file. That step is waived for v3.35.0 only; the waiver does not extend to later versions. It is recorded in `handoffs/CORRECTIONS_v3.35.0.md` on `main` after publication. Publication is evidenced by the annotated tag and the GitHub Release object, not by this field.

### Template CI

Twelve of the 13 template repositories have a CI workflow; the document-processor template has none. This release makes no claim about template CI results.

## Upgrade and compatibility

Read the release handoff (`handoffs/RELEASE_HANDOFF_v3.35.0.md`) and the deployment specification (`DEPLOYMENT_SPEC_v3.35.0.yaml`) from the peeled public tag before installation, and apply every row of `handoffs/CORRECTIONS_v3.35.0.md` on `main`. Preserve receiver-owned extensions and compare local modifications before replacing framework files. Python 3.10 or newer is required.

Install `/aget-propose-actions` only together with both scripts it calls, `scripts/propose_actions_handoff_scan.py` and `scripts/propose_actions_classify.py`. A skill without its scripts is an incomplete install. An Aget that keeps handoff documents outside `docs`, `planning` and `inbox/outbound` lists its locations in `.aget/config.json` under `propose_actions.handoff_locations`; otherwise the scan does not look there.

The strict close gate needs three files together: `scripts/close_gate_check.py`, `scripts/close_gate_lifecycle.py` and `specs/AGET_PROJECT_PLAN_SPEC.md`. Take all three from the same tag. If the specification is missing or lacks the lifecycle rows the gate reads, the gate fails closed with a schema error (exit 3). The framework's `/aget-close-project` skill replaces the earlier template copy and is substantially rewritten, with an entry-phase gate, an exit-phase gate and a required `--disposition`. Merge local customizations into it; do not overwrite them.

If your Aget installed the 3.31.1 close-gate package, it may carry its own copy of `tests/test_close_gate_receiver_contract.py` and `handoffs/DELIVERED_FILES_v3.31.1.yaml`, rebound to your repository. Taking the 3.35.0 `specs/AGET_PROJECT_PLAN_SPEC.md` turns such a copy red if it pins the earlier specification digest. Either refresh the test from this release, which reads the 3.31.1 tag and skips with a declared precondition where that tag is absent, or keep the local skip you already carry. Do not overwrite a local skip without replacing it. Record which you chose in your receipt.

Publication, installation, behaviour verification and acceptance are separate states. No receiver adoption is asserted here. A receiver-owned receipt must name its actual source pins, credited capability and exercised rejection path; producer-written receipts do not count.
