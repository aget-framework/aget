# v3.33.0 — Make the Next Migration Cost Less

**Target release date**: 2026-08-30 · **Type**: non-breaking minor release
**Artifact state**: prepared from candidate `2e7d11bc4af32fdd29655d516b24210723987b28`;
publication, tag identity, and downstream adoption are separate predicates

## Why this release exists

The locked scope contained finished work that could not all travel to the public framework. Several
items were instance extensions, one claimed repair had not landed, and three reusable artifact classes
had no canonical directory in which to live. Treating every locked row as shipped would have hidden that
boundary instead of fixing it.

v3.33.0 therefore publishes only the parts that have a truthful canonical form. It also creates three
small destination contracts so later work can be promoted without inventing a home during a release.
Those directory contracts are infrastructure for a future promotion; they are not evidence that the
deferred controls themselves shipped.

## What is in the candidate

### Checks that can distinguish their subjects

- `scripts/check_archetype_register_parity.py` compares the authoritative archetype register with the
  consumer mapping, available template roles, and declared fleet roles. Missing populations are reported
  as `UNAVAILABLE`, not silently treated as empty. `tests/test_archetype_register_parity.py` exercises
  aligned and divergent populations, reader failures, and CLI exit semantics.
- `scripts/self_assess_conformance.py` reports three local conformance questions without editing its
  subject: unlanded content rejected by an existing boundary control, declared controls with no actuator,
  and L-doc index coherence. `tests/test_self_assess_conformance.py` supplies the missing actuator and
  demonstrates both incriminating and exonerating results. A clean test run proves the instrument can
  discriminate; it does not assert that every receiving seat is conformant.

### Search that opens the surface it names

`scripts/study_topic.py` now decomposes URL-shaped input into meaningful terms, includes initiative
manifests and their proposals in the research surface, and opens YAML as well as Markdown in the
knowledge/ontology tier. The update prevents a link or a governed ontology term from becoming a
confident false "novel topic" solely because the instrument never opened the relevant surface.

Because this payload changes the file named by the still-live v3.30 migration contract,
`handoffs/FLEET_MIGRATION_CONTRACT_v3.30.0.json` records the new current digest while preserving the
v3.30 tag digest. Existing receipts remain readable against the bytes they actually verified; this
amendment does not assert that the supervisor-owned migration wave completed.

### Public shapes without private instance content

- `docs/REFERENT_REGISTRY.yaml` carries the reusable, audience-aware referent classification. The
  instance-local resolver that originally consumed it is not part of this release.
- `sops/templates/RELEASE_HANDOFF_TEMPLATE.md` carries the public handoff shape without an operator's
  private fleet roster.
- `.aget/patterns/README.md`, `.githooks/README.md`, and `planning/README.md` define where executable
  patterns, repository-managed hooks, and shared planning templates belong. They create canonical homes;
  they do not claim that a commit-message hook, content sanitizer, or project-plan template has landed.

## What is deliberately not claimed

The release disposition is narrower than the locked scope:

- R1's boundary-control payload is deferred in full. Only the three destination contracts described
  above ship as an explicitly authorized follow-on.
- R4 and R5 ship only their canonical-shaped pieces: the public handoff template and referent registry.
  Their instance-local scripts do not ship.
- R2, R3, R8, R9, and R12 remain deferred because their landed implementations are instance artifacts.
- R11 remains deferred because the claimed detection repair did not land; removing a flag is not the same
  as making the checker detect the terminal row.

No deferred row is counted as delivered by the release notes or deployment specification.

## Verification and receiver boundary

The focused candidate checks are:

```bash
python3 -m pytest -q tests/test_archetype_register_parity.py
python3 -m pytest -q tests/test_self_assess_conformance.py
python3 -m pytest -q tests/test_study_topic_ontology_surface.py
python3 -m pytest -q tests/test_fleet_migration_contract_digests.py
```

These commands verify the promoted mechanisms in a candidate checkout. They do not establish that a tag
exists, that every template repository carries v3.33.0, or that a downstream seat installed and accepted
the release. A receiver must acquire the immutable `v3.33.0` tag, record its peeled commit, run the
release handoff's local checks, and preserve its own acceptance result.

## Compatibility and rollback

The release adds reporting and search behavior; it does not rewrite receiver-owned plans, goals, agent
state, or fleet registers. If a promoted instrument is unsuitable at a receiving seat, restore that
seat's v3.32.0 pin or prior commit, preserve the failing fixture and command output, and keep adoption
parked. Do not reinterpret publication as successful migration.
