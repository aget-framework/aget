## Context for External Fleets

External fleets must treat availability, acquisition, installation, behavioural verification and acceptance as separate states. This handoff is an information and verification contract, not authority to modify a receiver. Each receiving manager applies its own governance, preserves local extensions, and returns evidence from the receiver itself. No operator-specific path, private inventory or fleet-wide deployment claim is embedded in this public artifact. In this handoff "your principal" means the person your supervisor answers to; "the maintainer" means the person who maintains this framework.

### What is the migration kit?
- **Problem it solves**: the earlier tools named one release in their own code, so each release needed a hand edit of every tool that named it; and the launch and push tools did not themselves check that an approval was a line your principal had typed.
- **What it does**: 37 files (34 Python) under `scripts/migration_kit/` that a supervisor runs batch by batch: prepare a batch (the prepare tools read the members' files and run git queries in their repositories; the files they write are their own outputs, at or beside the paths the operator names, and a fresh packet-relative stage under `<packet folder>/<release>/packets/`, outside every git repository, every member and the framework clones), rehearse it on copies, record your principal's typed line, apply the protected files, launch each receiver's own session, check the suite at the exact commit to be pushed, push, and read the result into a ledger. The kit carries no default release: it reads the source and target versions from `.aget/migration_target.json`. Nine tools (the prepare, plan, apply, packet-rehearsal, push, ledger and readiness tools) stop without a target and say so; the others, among them `launch_batch.py`, `record_authority.py`, `rehearse_v37.py` and `suite_at_commit.py`, make no such check.
- **Typed-line checks, with stated limits**: the push, and a launch without `--copy-root`, refuse (exit 6) unless a recorded line is found typed in a session transcript: a transcript whose name starts with the session id the record names, or, when it names none, any transcript in the folder searched (by default the Claude Code transcript folder of the repository the kit sits in; `AGET_MIGRATION_PROJECTS_DIR` replaces it). A line the harness recorded as a human entry made mid-turn is also accepted, although the tool does not read whether it was typed; wherever this handoff says a line is found typed, that case is included. The tool does not check that the session is the open one; typing the line in the open session is an operator rule, not enforced by the tool. A launch with `--copy-root` checks no typed line. A launch line need not name the launch. A push reads only a push line recorded for it (`record_authority.py --act push`); the batch's launch line is never push authority. The push line must have one fixed form (the prefix, then `push the commits of batch N`, optionally more batches (`batches 10t and 10`) and ` with commit SHA` (or `commits SHA, SHA and SHA`, each 7 to 40 hexadecimal characters), and nothing else; with the default prefix, `GO supervisor - push the commits of batch 1`), and must equal the whole of the newest prompt it is found in (runs of whitespace collapsed; a pasted block among other words is left out of the comparison). That is a test of form, not a reading of meaning: a line worded any other way is refused, an affirmative one too, and your principal types the form. A line found only in the session's first prompt, which a launch argument also produces, is refused: `check_principal_line.py` exits 5 on it, `record_authority.py` does not record it (exit 1), and a launch or push relying on it exits 6. See "Authority checks" under Known Items.
- **What it does not do**: it ships no membership tool and no ingest tool (the procedure has both done by hand, membership on the unmet rows that `fleet_ledger.py` prints); it is not a template payload; it is not shown with any command-line tool other than Claude Code.

### What is the kit batch procedure?
`sops/SOP_fleet_migration.md` v1.10.8, section "Kit Batch Procedure". It has a per-release setup table ("Set up once per release"), a table of per-release inputs (Part A) and fifteen fixed steps, B0 to B13 with B8a (Part B), each naming its tool, its pass condition and who acts. Gate 5.5 of the same document adds a close-out gate for the whole migration. The procedure states that a batch is run from that section alone; where you need another document, record which one in step B13.

### What is CAP-VOC-006?
A capability retained from v3.35.1 in `specs/AGET_VOCABULARY_SPEC.md` v1.18.0, "Grounded Term Display Form": it governs how a highlighted vocabulary term is written in prose. The same version adds the verification rows V-VOCAB-011 to V-VOCAB-016, scopes the earlier prose rules to the specification's own register, and revises the `Aget_Instance` entry. It shipped in v3.35.1 and is unchanged in v3.36.0. No file is installed at a receiver for it; four of its six verification rows are marked "canonical check owed", so their automated checks are not shipped yet.

## Upgrade Guide

Two routes exist. The per-Aget route below is the same as for earlier releases. The kit route was exercised by the second outcome run with two worker fixtures from 3.35.1 to 3.36.0, returning FAIL accepted as R59 named limits (see "What was shown, and what was not"). Real-fleet deployment is unverified; a supervisor should report what it meets. Neither route gates the supervising Aget's own migration.

### Per-Aget route

Run this block as one Bash script; stop on any failed command. It reads payload bytes from tag objects and checks nothing out, so a source clone shared by several Agets is never switched under another migration.

```bash
set -euo pipefail
export SOURCE=/path/to/aget
export TEMPLATE=/path/to/matching-template
export AGENT=/path/to/receiving-agent

git -C "$SOURCE" fetch --tags origin
test "$(git -C "$SOURCE" cat-file -t refs/tags/v3.36.0)" = tag
CORE_SHA=$(git -C "$SOURCE" rev-parse --verify 'v3.36.0^{commit}')
```

### Stops

Stop at the first failed step and record it, naming the step. INCONCLUSIVE is never PASS. In particular:
- A tool that reports no release target, or a missing `records.json`: complete the setup; do not edit the tool.
- Launch or push exits 6: the one recorded line the tool reads for that batch and act (for a launch, the first usable `:launch` entry, otherwise the first usable matching batch entry without an act suffix; for a push, the first usable `:push` entry only, never the batch's line; entries for another act or without a line are skipped) does not pass its checks, or there is no such line, or the records file is missing or unreadable. Check the setup first; if the setup is complete, ask your principal for the line and end your turn on the request.
- `check_principal_line.py` exits 5: the line is only in the session's first prompt, which a launch argument also produces (a launch or push then exits 6 and gives the same reason). Your principal types it again once the session is running.
- A principal line that withholds or conditions the push, in any wording: do not record it as push authority. The tool refuses every push line that does not have the one fixed form ("hold the push until I review", "the push remains unapproved" and "push tomorrow" are refused, and the reason states the form), and it refuses when the typed prompt holds other words before or after the line (a pasted block among other words is left out of that comparison). This is a test of form, not a reading of meaning: an affirmative line worded another way is refused too, and your principal types the form. A withholding that exists only inside a block pasted beside the line, or in a later prompt that does not repeat the line, is not read, and declining to record the push then is an operator rule, not enforced by the tool. The push needs its own recorded push line (`record_authority.py --act push`); the batch's launch line is never push authority. A commit the line names requires a matching `--extra-commit`, the shorter id a prefix of the longer; when HEAD moved since the launch check, the extra-commit route compares HEAD with the longer id; with HEAD unchanged, a supplied extra commit does not change the checked commit the gate permits; a push whose line names a commit is refused when no `--extra-commit` is given.
- A member the list marks `blocked` at B1 (its receiver bounds check did not pass and no override is recorded): it does not go forward without a recorded override; otherwise drop it with its reason. A drop or a `blocked` mark is in the write list only: the apply step skips the member, but the launcher reads the packet and still launches it. After a drop, rebuild the packet without the member, or name the remaining members with `--only` at every launch (B6, B8), and select them explicitly at apply and push. Operator rule, not enforced by the tool.
- A finding from a receiver's blocking gate at B1 (a check that a hook, a workflow or the member's suite runs): raise it for a ruling before B2.
- B8a (suite at the exact commit to be pushed) reads FAIL: no push. See Known Items for the two cases. B8a reads INCONCLUSIVE: no push either, and a baseline-equal ruling does not cover it. A suite that moved the clone's HEAD already read INCONCLUSIVE; the command-line tool now reads it too when the pre-push hook moved the clone's HEAD, or when the suite or the hook left, outside the paths named with `--allow-path`, a new `git status --porcelain` line, a line that is gone, or any other change to a file, link or folder of the working tree that git does not ignore, tracked or not (an untracked file under a `__pycache__` or `.pytest_cache` folder is left out).
- Exit code 0 from a launch or a push is not a pass. A live launch at B8 exits 0 whatever its after-run checks said, and when the push tool's gate refuses a receiver it prints NOT PUSHED and that refusal does not make the exit code non-zero. Read the printed verdict for each member.
- A refusal by the harness or its permission classifier of a step your principal authorized: report the step, the refusal's reason verbatim and the authorizing line. Never retry it in another form or route around it.
- A change of Claude Code version within a batch: launch refuses the mismatch. No restart or update inside a batch.
- At every step: no receiver write except by B7's reviewed script or the receiver's own session; no push without B9; no history rewrite; workflows and subagents never approve, apply, launch, push or commit.
- Never end a turn on an act handed to a receiver without `watch_receiver.py <receiver folder>` armed.

The session rule `Bash(python3 scripts/migration_kit/launch_batch.py:*)` covers the command with any arguments. Using `--copy-root` only for rehearsals is an operator rule, not enforced by the tool beyond those folder tests.
- A launch line need not name the launch. In addition to the provenance, prefix, length and batch checks, the recorded line must not match the tool's recognized launch-exclusion pattern. Only a push must be named.
- The launch check binds the batch's name; the push check binds the packet. When the launch tool calls the check, it passes the packet's `batch` value and nothing else of the packet, so another packet file with the same `batch` value passes the launch check on the same recorded line, whatever receivers it lists; launching with the packet that was prepared and rehearsed for that batch is an operator rule, not enforced by the tool. A push line is recorded for one packet file (`record_authority.py --act push --packet`, which refuses without `--packet` and keeps that file's digest with the line), and `push_batch.py --push` refuses a push from any other packet file, even one with the same `batch` value.
- A push reads only a push line recorded for it (key `<batch>:push`, written by `record_authority.py --act push`); the batch's launch line is never push authority, whatever it says. The push line must have one fixed form: the prefix, then `push the commits of batch N`, optionally more batches (`batches 10t and 10`) and ` with commit SHA` (or `commits SHA, SHA and SHA`, each 7 to 40 hexadecimal characters), and nothing else. With the default prefix: `GO supervisor - push the commits of batch 1`. Runs of whitespace are not compared, and after the prefix letter case is not compared either; the prefix itself keeps its letter case (`go supervisor - ...` is refused). Every other line is refused, and the reason states the form: "the push is not approved yet", "hold the push until I review", "the push remains unapproved", "the push is prohibited", "the push is held" and "push tomorrow" are refused. This is a test of form, not a reading of meaning: an affirmative line worded another way ("batch 1, push the verified commits", "no problem, push it") is refused too, and your principal types the form. A commit the line names requires a matching `--extra-commit`, the shorter id a prefix of the longer; when HEAD moved since the launch check, the extra-commit route compares HEAD with the longer id; with HEAD unchanged, a supplied extra commit does not change the checked commit the gate permits; a push whose line names a commit is refused when no `--extra-commit` is given.
- The shape, exclusion and push-form tests read the line as recorded; the batch is read from the first batch list of the typed prompt that holds the line. For a launch the tool accepts the recorded line when it is part of what was typed, so words typed around it are not read by the shape and exclusion tests. For a push the newest prompt that holds the line must equal it once runs of whitespace are collapsed: a recorded "... push the commits of batch 1" is refused when that prompt went on "... tomorrow, not today". A pasted block among other words is left out of that comparison, so a condition that exists only inside such a paste is not seen. A baseline-equal ruling line gets the same whole-prompt test and has its own fixed form: the prefix, then `the failures at SHA are baseline-equal`, SHA being 7 to 40 characters the commit's id starts with; a ruling worded any other way is refused.
- Operator rule for a push, not enforced by the tool: nothing is recorded as push authority when the principal withholds or conditions the push where the tool does not read it. For a push the tool refuses unless the recorded line has the fixed form and the newest prompt that holds it equals it (whitespace runs collapsed; a pasted block among other words is left out of the comparison). It does not read meaning: a condition inside a block pasted beside the line is not seen, and a later prompt that revokes the push without holding the recorded line is not read.
- `prepare_write_list.py --drop` marks a member blocked in the write list only. The apply step skips a blocked member, with or without `--only`. The launcher reads the packet and never the list, so a dropped member is still launched (in a packet prepared with `--placed-by-apply`, as the procedure's B1 prepares it, a migrating member gets a baseline session and a migration session, told its files were already placed and to set the version and commit) unless the packet is rebuilt without it or the remaining members are named with `--only` at every launch. The push tool does not read the list either: it refuses a member that has no launch evidence, so a dropped member that was never launched is not pushed, and one that was launched by mistake is not held back by the drop.
- `--extra-paths` and `--allow-dirty` on `push_batch.py` come from the command line alone; no typed line is compared. `--extra-commit` must be a commit the recorded push line names (` with commit SHA`, the shorter id a prefix of the longer). When HEAD moved since the launch check, HEAD is compared with the longer matching id; with HEAD unchanged, a supplied extra commit does not change the checked commit the gate permits.
- Exit code 0 is not a pass. A live launch of the members' sessions (B8) exits 0 whatever its after-run checks said. `push_batch.py` prints NOT PUSHED for a receiver its gate refuses, and that refusal does not make the exit code non-zero. Read the printed verdict for each member.
- Some help texts, printed messages and generated receiver prompts in the kit still state stronger authorization or copy guarantees than the tools establish: a launch prompt says the session was launched on the principal's authorization even on the unchecked `--copy-root` route, the push options' help says a value was named or allowed in the principal's line although nothing compares them, and the `--copy-root` help calls the folder a throwaway copy without proving it. These strings are unchanged in this release. They are not evidence of authorization.
